# Промпт исполнителя тикета

Шаблон для `Agent` (general-purpose, в фоне). Исполнитель стартует с пустым контекстом,
поэтому промпт самодостаточен: где работать, что читать, как проверять, как коммитить,
что доложить. Плейсхолдеры в фигурных скобках заменяются; лишние разделы удаляются.

---

Ты исполнитель одного тикета по конвейеру mattpocock (implement → tdd → code-review).
Работай в {РАБОЧАЯ ДИРЕКТОРИЯ: «своей текущей директории — это git-worktree репозитория X с
созданной для тебя веткой» | «worktree <путь>, ветка <имя>»}. Ветки не переключай, ничего не
пушь, в целевую ветку не вливай. {ПРОДОЛЖЕНИЕ ЧЕРНОВИКА: в дереве лежат незакоммиченные
файлы прошлого исполнителя — перечислить; прочитай их первыми и продолжай, а не переписывай
заново; ответственность за их содержимое теперь твоя, нашёл дефект — чини. Правки, которые
он принял и не успел внести: перечислить.} {ЧУЖИЕ ФАЙЛЫ: незакоммиченные изменения в
рабочем дереве — перечислить — не стейджить и не трогать.} {СОСЕДИ: параллельно другой агент
делает тикет Z в отдельной worktree; общие файлы — перечислить — дополняй, а не переписывай.}

## Тикет

{ИМЯ ТИКЕТА} — «{заголовок}»:

```
gh issue view {N} -R {owner/repo} --comments     # тикет
gh issue view {M} -R {owner/repo}                # родительская спека, разделы …
```

{СУТЬ: три-восемь предложений своими словами — что должно заработать, где границы,
что НЕ входит. Фактов, которые исполнитель не найдёт сам, здесь больше, чем пересказа
тикета: имена ключей, известные особенности парсеров и хуков, где лежит образец.}

3. Файлы скиллов конвейера (сначала Skill tool `mattpocock-skills:tdd` и

   - {путь к}/skills/engineering/implement/SKILL.md

{ТРЕКЕР: если трекер живёт в другом репозитории — сказать, чтобы code-review не просил

Большие выводы команд и файлов не печатай целиком — режь `head`/`tail`/`grep` или читай
файлы по частям: дампы переполняют контекст и обрывают работу.

## Технические указания

- {ЗАВИСИМОСТИ: где ставятся, что запрещено (ноль зависимостей / только в папке X).}
- {ШОВ: точная сигнатура чистой функции или модуля, на котором стоят тесты, и список
  случаев, которые тесты обязаны покрыть.}
- {ПЛАТФОРМЫ: если набор тестов гоняется в CI на нескольких системах, он обязан быть
  платформенно-нейтральным — POSIX-пути там, где логика работает с POSIX-путями,
  нормализация переводов строк, честный пропуск того, что требует чужой системы. Набор,
  который ни разу не шёл на второй платформе, не зелёный, а неизмеренный.}
- {ДАННЫЕ ОПЕРАТОРА: боевые файлы (сохранения, `.env`, базы) — только чтение; проверять
  их mtime до и после; личные данные в отчёт не переписывать. Мутирующие команды — в
  песочнице: HOME подменяется дочернему процессу через обёртку, не глобально.}
- {ЖИВАЯ ПРОВЕРКА: что запустить и что увидеть; какая переменная окружения делает
  проверку повторяемой без боевых команд. Гаси **только свои** процессы, по pid; поиск
  по имени (`pkill -f`) убивает соседей.}
- Подчинённые агенты ревью работают **на чтение**: `git stash`, смена веток и любые
  мутации состояния репозитория им запрещены.
- {ЯЗЫК: всё видимое пользователю — по-русски; идентификаторы латиницей.}

## Порядок

1. База: {команды тестов и линтера} — числа и статус до правки.
2. TDD на шве: сначала красные тесты, потом код до зелёного; одиночные файлы тестов по
   ходу, полный набор один раз в конце.
3. {СБОРКА/ЖИВАЯ ПРОВЕРКА.}
4. Полный набор тестов, линтер и сборка зелёные. {ДОКУМЕНТЫ: что обновить; `CLAUDE.md` —
   не править, предложить текст в отчёте, если он на красной полосе проекта.}
5. Code review собственной правки по двум осям: стандарты репозитория и соответствие
   тикету/спеке. Исправить найденное.
6. Коммиты в {ветку} в стиле репозитория ({пример формата, `git log --oneline -10`}).
   Стейджить только свои файлы. Каждое сообщение завершать трейлерами:

```
Co-Authored-By: {модель} <noreply@anthropic.com>
Claude-Session: {ссылка на сессию}
```

{БАЗА ВЕТКИ: если ветка растёт от чего-то, что координатор потом переложит, — сказать
это прямо и назвать хеш, чтобы исполнитель не пытался слить целевую ветку сам.}

## Отчёт в конце

Кратко: что сделано и где (модули и интерфейсы, без кода); {ФАКТЫ, которые нужны
следующим тикетам: имена ключей, переменных, папок}; число тестов до и после, статус
линтера; результат живой проверки (что видел; mtime боевых файлов до и после); хеши
коммитов, ветка, путь к worktree; правки вне своей области; расхождения с тикетом и
спорные решения — с причиной; что оператору проверить руками. {КОНТЕНТ НА ВКУС: полный
текст всего написанного — оператор читает и правит по отчёту, слияние только после его
одобрения.}
