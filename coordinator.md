# Координатор: публикация, запуск, приём, слияние

## Публикация тикетов (GitHub)

Порядок — блокеры первыми, чтобы в теле каждого тикета стояли настоящие номера.
Скриптом (python + `gh`): создать issue по очереди, из URL взять номер, подставить в
«Blocked by» следующих; затем нативные зависимости:

```
gh api repos/{owner}/{repo}/issues/{n} --jq .id                       # database id блокера
gh api --method POST repos/{owner}/{repo}/issues/{child}/dependencies/blocked_by \
       -F issue_id={blocker_db_id}
```

Тело тикета по шаблону `to-tickets` (`## Parent`, `## What to build`, `## Acceptance
criteria`, `## Blocked by`), метка `ready-for-agent`. Ответ трекера «зависимости
недоступны» — строка «Blocked by» в теле остаётся единственной связью.

## Запуск исполнителей

- **Фронтир** — тикеты, у которых все блокеры влиты. Пересчитывать после каждого
  слияния.
- **Своя worktree каждому**, включая того, кто по смыслу «работает в целевой ветке»:
  основная рабочая копия остаётся координатору. Это снимает три беды разом —
  перемешанные `git add`, гонку за одними и теми же файлами и погашенные чужие
  процессы. `Agent` с `isolation: "worktree"` заводит копию сам; в другом репозитории —
  руками: `git -C <repo> worktree add <path> -b <branch> <base>`; путь и ветка идут в
  промпт.
- **Параллельно** — только тикеты без общих файлов. Общие документы (`README`,
  `CONTEXT.md`) конфликтуют почти всегда: это нормально, исполнитель их **дополняет**, а
  разрешает координатор, сохраняя оба намерения.
- Не запускать больше исполнителей, чем успеваешь принять и слить: очередь из отчётов
  стареет вместе с базой их веток.
- **Пересечения между репозиториями** (генератор из репозитория A пишет производные
  в репозиторий B, где работает другой агент): исполнитель кладёт результат в
  scratchpad, координатор применяет его сам после освобождения дерева.

## Приём отчёта

1. Отчёт читается целиком: числа, хеши, расхождения, «спорное», «проверить руками».
2. Утверждения проверяются на целевой ветке **своими** командами: полный набор тестов,
   линтер, сборка, `git status` (чужие файлы не тронуты), `git log` (трейлеры, стиль).
3. Найденные исполнителем дыры в документах и словаре закрываются сразу отдельным
   коммитом координатора (`docs(context): …`).
4. Расхождения с тикетом делятся на три корзины: принято (объяснимо и лучше буквы
   тикета), спорное (оператору списком, у каждого пункта рекомендация), красная полоса
   (не вливается без явного «да»).
5. Контент на вкус (тексты персонажа, визуал) — оператору целиком, ветка ждёт «ок».

## Слияние — линейно

```
git -C <worktree> rebase <target>          # ветка исполнителя поверх целевой
git merge --ff-only <branch>               # из целевой ветки
<полный набор тестов, линтер и сборка на целевой>
git worktree remove --force <worktree>; git branch -d <branch>
```

Целевая ветка с чужими незакоммиченными файлами: ff-слияние их не трогает, но ветка
исполнителя не должна касаться тех же файлов. Отдельный коммит красной полосы остаётся
на ветке до решения оператора: `git merge --ff-only <хеш до него>`.

## Обрыв исполнителя и уехавшая база

Агент падает на лимите модели или ошибке среды посреди работы. Его **незакоммиченные
файлы остаются в дереве** — это ценность, а не мусор.

1. Снять состояние: `git -C <worktree> status --short` — новые и правленые файлы.
2. Записать их в передачу вместе с правками, которые он принял по ревью и не успел
   внести (они видны в его последней реплике).
3. Перезапустить исполнителя **в том же дереве**, велев продолжать черновик, а не
   переписывать, и передав список принятых правок. Ответственность за чужой код —
   на новом исполнителе.

**База уехала**, если пока он работал, его блокер был переложен и влит под другими
хешами. Тогда обычный `rebase` попытается применить чужие патчи повторно. Переносить
только его коммиты:

```
git -C <worktree> rebase --onto <target> <старый tip блокера> <его ветка>
```

Старый хеш взять из передачи — записывать его туда в момент, когда перекладываешь
блокер, а не искать потом в reflog.

## Окружение после слияния

Всё, что делает влитое видимым для следующих тикетов (переустановка плагина, обновление
кэша, регенерация производных), координатор выполняет сразу — в пределах разрешений,
записанных в передаче.

## Экзит-код — сигнал, а не украшение

Команда, чей код возврата и есть ответ (`gh run watch --exit-status`, тесты, линтер),
запускается **одна**, без хвоста `; echo; tail`: иначе код придёт от последней команды
цепочки, и «зелено» окажется неправдой. Проверено на себе: так был прочитан успешным
упавший выпуск.

## Заблокирован снаружи — ищи путь через то, что уже есть

Внешний шаг (публикация, релиз, выкатка), упёршийся в чужой секрет или недоступную
панель, не обязан возвращать человека к рутине. Сначала — путь на уже имеющихся
учётных данных: локальный `gh`, готовые артефакты сборки, ручная выкладка. Оператору
остаётся то, что физически требует его: выпустить токен, войти в чужой кабинет,
принять решение о деньгах. Токен или пароль в переписке не запрашивается и не
используется; появился — сказать прямо и посоветовать ротацию.

## Закрытие тикета

Закрывать доказательствами, а не словом «готово»: хеши коммитов, числа тестов до и
после, что проверено на целевой ветке, что измерено живьём, что осталось человеку.
Через месяц это единственное, по чему видно, чем тикет кончился.

## Отчёт оператору

Коротко, по факту, после каждого слияния или на вопрос «как дела»:

- что влито (тикет, хеши), числа до/после, что проверено на целевой ветке;
- что найдено сверх тикета и как поступили (принято / закрыто / спорное с рекомендацией);
- кто работает сейчас, что стартует следом;
- что ждёт оператора: вкусовой контент, продуктовое решение, ручная приёмка.

Своя ошибка (действие мимо границ, затёртый файл, неверно прочитанный экзит-код) — в том
же отчёте, первой строкой, с последствием и предложением правила на будущее.
